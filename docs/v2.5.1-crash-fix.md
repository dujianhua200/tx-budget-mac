# v2.5.1 事故记录：点“补全并校正定额库”真机闪退（随 v2.6.0 发布）

> 本修复原定 v2.5.1 单发；2026-10-23 用户裁决“先不推送，还有很多问题”，
> 与真机问题批次合并为 v2.6.0 发布。本文档记录根因与防回归措施。

## 现象

v2.5.0 真机（macOS 27.0.1）点击“补全并校正定额库”立即闪退。
崩溃日志关键帧：

```
Exception: EXC_BREAKPOINT (SIGTRAP) / _assertionFailure
frame 1: closure #1 in variable initialization expression of static NSBundle.module
frame 5: LibraryMaintenanceControls.prepareCompletion()
```

崩溃发生在试算（prepareCompletion）阶段、任何数据写入之前，用户数据无损。

## 根因

`Logic/FullLibrary.swift` 用 SwiftPM 生成的 `Bundle.module` 访问器读内置
完整库 `full-library.json`：

```swift
Bundle.module.url(forResource: "full-library", withExtension: "json")
```

`Bundle.module` 的生成代码在**打包后的 .app 布局**下找不到资源包时不是
返回 nil，而是直接 `assertionFailure` 闪退——`loadBundledFullLibrary()`
里“资源缺失返回 nil 并提示”的 `guard` 根本没机会执行。

`scripts/bundle.sh` 虽然已把 `TXBudget_TXBudget.bundle` 拷进
`Contents/Resources` 并做了存在校验，但在用户机器（macOS 27 + 手工组装
的 .app）上，该访问器的查找路径仍然落空。这是全仓唯一一处
`Bundle.module` 使用（修复时已 grep 确认）。

## 为何 CI 测不出

`swift test` 的运行布局里，SwiftPM 资源包就在构建产物目录（.build）旁，
`Bundle.module` 查找必然成功——199 个测试全绿也照不出打包布局问题。
这条路径（真机 .app 内点补全并校正）在 v2.5.0 之前从未被真机点过：
入口埋得深，直到 v2.5.0 把它放进菜单栏才第一次被真机触发。

## 修法

1. **彻底弃用 `Bundle.module`**：`loadBundledFullLibrary()` 改为显式、
   永不 trap 的纯 FileManager/Data 查找，候选顺序（纯函数
   `fullLibraryCandidateURLs`，单测钉死）：
   ① `resourceURL/TXBudget_TXBudget.bundle/full-library.json`；
   ② `resourceURL/full-library.json`（松散副本）；
   ③ `bundleURL/TXBudget_TXBudget.bundle/full-library.json`；
   其后在 resourceURL 与 bundleURL 下限深 4 层递归兜底找 `full-library.json`。
   全部找不到返回 nil，走既有 toast 提示，绝不闪退。
2. **打包双保险**：`bundle.sh` 除资源包外，再把 `full-library.json` 松散
   拷一份到 `Contents/Resources/` 根；打包末尾双断言两处都在，缺一即停。
3. **CI 防回归断言**：build.yml 新增 “Verify DMG contents” 步——挂载产出的
   DMG，断言 `.app/Contents/Resources/full-library.json` 与
   `.app/Contents/Resources/TXBudget_TXBudget.bundle/full-library.json`
   均存在，并把 `ls` 输出留在 CI 日志里。打包布局问题从此在发布前拦截，
   不再等真机踩。
4. 测试：`FullLibraryLookupTests`（候选顺序、resourceURL 为 nil、递归深度
   语义）3 个；打包后在本地镜像核对 DMG 内容断言的检查项与 bundle.sh
   落盘路径一致。
