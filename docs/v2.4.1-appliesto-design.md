# v2.4.1 设计：规则「适用工程」（appliesTo）过滤语义补全

## 1. 问题

`RuleRow.appliesTo`（适用工程）在 Swift 引擎中从未被消费：仅存储、导入导出携带，
引擎 `Rule` 类型甚至不带这个字段（`RuleRow.toEngine()` 直接丢弃）。标了“仅适用
某些工程”的材料规则目前对全部工程出量，表四会多算。

## 2. 语义来源（实测考证，不猜）

逐文件核查 Electron 仓库 `~/workspace/budget-app` 的结论，与此前假设不同，
必须如实记录：

- **Electron 的 `src/engine/calc.mjs` 同样从不消费 appliesTo**：规则循环只按
  kind（变体/变体*/通用/备选）分发，全仓 grep 显示 appliesTo 仅出现在
  `profiles.js` 的归一化（缺省 '全'）、`libraryDefs.js` 的编辑列、
  `excel.cjs` 的导出列与迁移测试的默认值断言中。
- Electron 自己的架构文档 `budget-app/docs/v2-design.md`（第 165–168 行）写明：
  appliesTo 沿用母版语义，**“后续增量如需按适用工程过滤，再在架构补充中定义”**
  ——即 Electron 时代就明确把过滤留作待办，从未落地。
- 因此本版即该待办增量，语义定义以 **v2-design.md + Excel 母版说明** 为准：
  - 母版 `build_template.py`：“一号多材：同一编号可有多行候选，「适用工程」
    填 \"全\" 或 \"1,3\"，空 = 不启用”；种子备注：“默认行适用工程 = 全”。
  - v2-design.md：`'' = 不启用，'全' = 全部工程，'1,3' = 仅工程序号 1,3`。

## 3. 语义定版

### 3.1 工程序号

母版里一个工作簿 = 一套库 + 多个并列工程（工程名称 1…N），序号即工程在该
工作簿中的 1 基位置。App 的对应物：**工程在其所属方案的工程集合中的 1 基
序号**——即 `db.projects` 中“有效方案与本工程相同”的工程按存储顺序排列，
本工程的位置（从 1 起）。有效方案的解析与 `calcFor` 完全一致（工程 profileId
命中则用之，否则回落激活方案）。工程不在 `db.projects` 中时（如取费页的示例
工程）序号取 1。

理由：规则存放在方案库中，其作用域天然是“用这套库的工程”；跨方案工程与
本库无关，不应挤占序号。

### 3.2 取值解析（共享纯函数 `Logic/RuleAppliesTo.swift`）

先去首尾空白（含全角空格）：

| 取值 | 语义 |
|---|---|
| `"全"` | 全部工程生效 |
| `""`（或纯空白） | **不启用**，任何工程都不生效 |
| `"1,3"` 等列表 | 仅序号在集合内的工程生效 |
| 无法解析出任何合法序号的非空串（如 `"abc"`） | 不启用（失败关闭） |

列表解析容错：分隔符接受半角逗号 `,`、全角逗号 `，`、顿号 `、`、分号 `;；`
与空白；全角数字先归一化；token 解析为整数且 ≥ 1 才保留（`0` 与非法 token
丢弃，`"1,a,3"` → {1,3}）。

### 3.3 生效范围与顺序

- 对全部四种 kind（通用 / 变体 / 变体* / 备选）统一生效——字段定义本身不限
  kind，资料库两个规则表（变体表、备选表）都带此列；内置库的通用规则
  appliesTo 恒为“全”，过滤对它们是恒等操作。
- 判定顺序：先过 appliesTo 闸门，再走 kind 逻辑。备选规则须同时满足
  appliesTo 与 ruleOverrides 启用才出量（两道闸门取交集，顺序不影响结果）。
- 孤儿定额规则原有跳过逻辑不变，闸门位置在其后、kind 分发之前。

## 4. 实现

| 位置 | 改动 |
|---|---|
| `Engine/EngineModels.swift` | `Rule` 增加 `appliesTo: String`（声明默认 `"全"`，init 增默认参数）；`Project` 增加 `projectOrdinal: Int`（init 末尾默认参数 = 1，现有两参调用 `calcProject(project, libs)` 全部兼容） |
| `Models/LibraryModels.swift` | `RuleRow.toEngine()` 透传 appliesTo |
| `Logic/RuleAppliesTo.swift`（新） | `parseRuleAppliesTo` / `ruleAppliesToProject(_:projectOrdinal:)` 纯函数，引擎与面板共用 |
| `Engine/Calc.swift` | 材料规则循环在 kind 分发前加闸门一行 |
| `Logic/ProfileLibs.swift` | 新增 `projectOrdinal(_ db:, _ project:)`；`calcFor` 注入序号后再调 `calcProject`（全 App 的计算入口都经 calcFor，导出/批量/校验自动同口径） |
| `Logic/WorkloadLinks.swift` | 面板判定同步闸门：被挡规则仍列出，合计按 0、`isEffective=false`、给原因文案（见 §5）；文件头注释同步 |
| `Views/WorkloadLinksPanel.swift` | 组装引擎 Project 时注入与 `calcFor` 相同的序号 |

资料库规则编辑界面**已暴露**「适用工程」列（`LibraryRowCodec` 第 48 行，
变体/备选两表都有），xlsx 导入导出也已携带，本版无需补 UI 列。

## 5. 面板展示

被 appliesTo 挡住但与本行相关的规则，照备选未启用的既有做法灰显
（`isEffective=false`、行透明度降低），原因文案：

- appliesTo 为空：`适用工程为空，本行不启用`
- 列表不含本工程：`适用工程为「1,3」，本工程序号 2，未生效`

一道规则同时被 appliesTo 与备选未启用挡住时，优先显示 appliesTo 原因
（先过闸门的先报告）。

## 6. 影响面（实测，2026-10-23）

| 数据 | appliesTo ≠ 全 的规则 |
|---|---|
| App 现行种子（Electron `data/seed.json`，117 条 rules） | **0 条** |
| v2.2.0 内置完整库（6,634 条 rules） | **0 条**（构建时恒写“全”） |

即随包数据升级后**没有任何工程的表四会变**。本语义只对用户自行填写/导入
了序号限制的规则生效（如从母版式 xlsx 导入、或在资料库手填“1,3”的行）——
这正是字段存在的目的，此前它们被静默忽略。

## 7. 测试

新增 `AppliesToTests`：解析单测（全/空/空白/列表/全角标点与数字/非法值/
混杂 token）、引擎行为（变体与通用规则在序号内/外的出量差异、空 = 永不
出量、备选 × appliesTo 交集）、`calcFor` 序号集成（同方案三工程只有第 2 个
出量，异方案工程不占序号）、面板-引擎一致性（灰显 + 原因 + 合计 0 ↔ 引擎
不出量；序号内两边同值）。

既有测试处置：全部测试夹具的 appliesTo 均为“全”（已逐一 grep 核实），
语义对它们是恒等操作，**预期零改动**；若实跑出现例外，逐个在汇报中列明。
