# v2.3.0 设计：按官方清理（删除官方手册没有的错误关联）

> 用户 2026-10-23 点名要求。v2.2.0 已把内置库按官方《通信451定额电子手册》
> v2022.12.716 重建（内置库内的错误关联已移除），且“补全并校正”只纠正命中行
> 的数值、**不删用户方案里的任何行**。本版本补上删除能力：把此前经 v2.1.0
> “补全”进入用户方案的错误关联、以及用户现行种子自带的额外关联，按官方口径清掉。
> 本功能是**删除操作**，按 §3 的三重保险实现，范围按 §2 写死。

## 1. 数据模型与模块

- 不新增数据字段、不改数据格式。作用对象是 `LibrarySet` 的三张关联表：
  `rules`（材料关联）、`quotaMachines`（机械关联）、`quotaInstruments`（仪表关联）。
- 新增纯 Logic 文件 `Sources/TXBudget/Logic/LibraryCleanup.swift`：
  - `planLibraryCleanup(base:full:) -> LibraryCleanupPlan`：dry-run，只读，
    返回三张表的待删清单（每行含 base 行 id、定额编码、名称、规格/编码、单位、消耗量）与计数。
  - `applyLibraryCleanup(base:plan:) -> (cleaned:report:)`：按 plan 清单逐行删除，
    返回清理后集合与实际删除计数。逐行按 (quota, 名称, spec/编码, unit, qty)
    全等匹配——真实数据中行 id 可能为空/重复（Electron 时代数据无 id，种子即如此），
    只按 id 删会误删整表（实测教训：种子三表 3,335 行 id 全为空）；清单里每一行
    都按谓词判定过，与之全等的行本身必是额外行，逐个删、删够清单条数为止，
    保证“预览什么删什么”。
  - `writeLibraryCleanupBackup(profile:directory:now:) throws -> URL`：删前备份，
    内容为 `DatabaseStore.exportProfileData` 的方案文件（与“导入方案文件”同格式，可直接恢复）。
- 对照对象 `full` 与补全/校正同源：内置完整库 `loadBundledFullLibrary()`
  （v2.2.0 起即官方校正版），不新增资源。
- 版本号 `TXBudget.version` 升至 2.3.0。

## 2. 清理判定（范围写死，超出范围一律不动）

一行关联被列入待删，当且仅当**同时**满足：

1. 行的定额编码存在于内置库（官方）定额表中（`full.quotas` 的 code 集合）；
2. 该行按判定键在内置库**同一编码定额**的关联中不存在。判定键与 v2.2 合并/校正一致：
   - 材料（rules）：`(quota, 归一化材料名, spec)`，归一化用 `libraryMatchNorm`；
   - 机械/仪表：编码键 `(quota, mcode)`（mcode 非空时）**或**名称键
     `(quota, 归一化名称)` 任一命中即视为存在（与 v2.2 的防重复判定同口径：
     编码不同但名称对得上的同一台班不删）。

明确排除（一律不删）：

- `rules` 中 `kind != "通用"` 的行（变体/备选是 App 自有的一号多材机制，
  v2.2 校正已排除，本次同样排除）；
- 定额编码不在官方内的行（手册外定额如 TGD2-161、用户自建定额的全部关联）；
- 定额本体、材料表（materials）、台班价两表、费率、工程数据——不碰。

注意口径：用户在官方定额下**自加**的关联同样会进待删清单——这是设计决定，
靠 §3 的预览清单把关（清单里逐行可见，用户可取消整个清理），不在判定层
区分来源（二者数据上不可区分，也不臆造来源标记）。

## 3. 安全设计（三重保险）

1. **先预览后执行**：资料库页点“按官方清理”先 dry-run；待删为 0 时只提示
   “没有官方之外的错误关联”；非 0 时弹出预览 sheet，按三张表分组列出**全部**
   待删行（定额编码 + 名称 + 消耗量）与分组计数，用户点“确认清理”才执行。
2. **删前自动备份**：确认执行时，先把当前方案完整导出为方案 JSON 写入数据
   目录（`DatabaseStore.defaultDirectory()`，与滚动备份同目录），文件名
   `cleanup-backup-<方案id>-<yyyyMMdd-HHmmss>.json`。备份失败则取消清理并报错，
   绝不无备份删数据。备份文件可经配置方案页“导入方案文件”恢复（导入生成新方案）。
   完成报告中写明备份文件路径。
3. **幂等**：清理后再跑 dry-run 必为 0 条（测试钉死）。

执行顺序固定为：预览（plan）→ 用户确认 → 写备份 → apply（按 plan 清单在
实时数据上逐行匹配删除）→ 完成报告（实际删除计数 + 备份路径）。apply 逐行
按内容全等匹配（见 §1），预览与执行之间即使数据有变动，也只删与预览行
全等的行，新出现的行不会被误删。

## 4. UI 入口与流程

- 位置：资料库页当前方案横幅区，与“补全并校正定额库”并列一行；按钮文案
  “按官方清理”，红色警告色（`.tint(.red)`）；旁注一句话说明作用与三重保险。
- 预览 sheet：标题“按官方清理 · 预览”，分组列出待删行（LazyVStack，可滚动，
  大清单不截断），顶部汇总三表计数与总计；底部“取消”/“确认清理”（destructive）。
  并注明“执行前会自动备份当前方案到数据目录，可用导入方案文件恢复”。
- 完成 alert：实际删除计数（三表分组）+ 备份文件路径。

## 5. 对引擎的影响面

- 引擎（Calc）只读三张关联表生成表三乙（机械）、表三丙（仪表）、表四（材料）。
  清理删除的是官方没有的多余关联，删除后这些定额的表三乙/丙、表四不再生成
  对应行——这正是清理目的（错误关联会让表三多出台班、多出材料）。
- 不影响：定额工日、费率、表一/表二/表五计算、导出格式、存量工程数据本身
  （工程引用的是定额编码，计算时按清理后的关联重新展开）。
- 风险点：用户自加关联被删（§2 已说明靠预览把关）；误删防护 = 判定键与
  v2.2 校正同口径 + 备份可恢复 + 测试覆盖排除范围。

## 6. 测试计划（基线 166 只增不减）

`Tests/TXBudgetTests/LibraryCleanupTests.swift`：

- dry-run 不改数据（base 前后全等）且清单命中预期行；
- apply 只删官方域内额外关联：变体规则保留、手册外定额关联保留、
  按名称命中的空码/异码行保留、定额本体/材料/价格逐字不动；
- 用户在官方定额下自加的关联出现在预览清单中（靠预览把关的断言）；
- 备份：apply 前写出的备份文件存在，解码后含待删行；
- 幂等：apply 后再 plan = 0；
- 端到端：含额外机械关联的工程，清理前表三乙含该机械、清理后不含，
  且官方机械行仍在；
- 真实数据：App 现行种子经 v2.2 补全并校正后跑清理，给出实测计数并钉死
  （这批是种子自带、补全校正保留下来的额外关联）。

## 7. 实测量级口径

以“App 现行种子 + v2.1.0 补全结果”为 base（复现用户在 v2.1.0 点过补全的
方案状态）跑一次 plan，与 v2.2 差异报告的“额外”计数（材料 790 / 机械 1,033 /
仪表 282）对照并解释口径差异：差异来源包括——种子自带额外关联（差异报告
只比对内置库之间）、机械/仪表名称键命中被保留的行、TGD2-161 等手册外
定额的关联被排除、种子 rules 多为变体 kind 被排除。数字以脚本实测为准，
写入发版汇报。

**实测结果（2026-10-23，脚本按本谓词复算，v2.1 完整库由转换脚本重跑生成、
计数与 v2.1.0 发布时一致）**：base = 种子 + v2.1 补全（定额 3,169、材料关联
6,233、机械关联 2,200、仪表关联 2,181）时，plan 待删合计 **1,822 条**：

| 表 | 待删 | 其中 v2.1 补全带入 | 其中种子自带 |
|---|---|---|---|
| 材料关联 rules | 824 | 790 | 34 |
| 机械关联 quotaMachines | 750 | 641 | 109 |
| 仪表关联 quotaInstruments | 248 | 218 | 30 |

与差异报告“额外”（790 / 1,033 / 282）的口径差异说明：

- 材料：v2.1 带入部分与差异报告 790 **逐条一致**；多出的 34 是种子自带的
  kind=通用额外规则（种子 rules 共 117 条，其余 83 条为变体/备选，不在范围）。
- 机械/仪表：差异报告按“同定额同名”匹配并把**同名重复行**（同一定额下同一
  台班出现多行、编码不同或空码）计为额外；本清理按 §2 判定（编码键或名称键
  任一命中即视为官方有此关联），同名重复行属于“官方有的关联的重复”，不在
  本功能删除范围（去重是另一回事），故机械 750 < 1,033、仪表 248 < 282。
  另有少量行在 v2.1 合并时因键与种子行相同未重复带入，来源归属随之变化
  （机械种子自带 109、仪表 30，与 Swift 真实数据测试的种子口径计数一致）。
