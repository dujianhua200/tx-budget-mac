## 3. 光缆主材单位：米，不是千米

**定位结论：错误在数据层。** 种子/用户库 `materials` 中
「光缆 GYTS_*/GYTA_*（18 行）、皮线光缆（1 行）」的 `unit` 写成“千米”；
引擎生成与界面显示都只是忠实取材料行 `unit`，无逻辑错误。
规则 `consumption = 1.007` 的语义是“千米/千米条”，与错误单位互相配套，
所以只改单位字符串会让生成量错 1000 倍，必须成对换算。

**修法（加载时一次性迁移，落在数据层、能真正修好用户现有数据）：**
- 纯函数 `migrateCableMaterialUnits(_ db: inout DbFile) -> Int`（Logic），
  由 `DatabaseStore.repair` 在每次加载时调用（repair 既有先例，迁移结果随
  下一次保存落盘）。
- 对每个方案库：`unit == "千米"` 的材料行 → `unit = "m"`（与内置完整库
  既有「光缆」行的单位一致，宇翔亦显示 m）；引用同一（名称|规格）的全部
  rules 行 `consumption × 1000`（1.007 → 1007 米/千米条）。价格不动
  （价格语义随单位由用户自理，与其“单位是米”的裁决一致）。
- 幂等：`MetaRecord` 新增可选字段 `appliedMigrations: [String]?`
  （容错解码，旧文件缺失 = nil），迁移后写入标记 `cable-unit-m-v26`；
  有标记则整体跳过——避免用户日后自建“千米”材料被误迁。
- 全库排查口径即“unit == 千米 的材料行”，种子内命中仅光缆/皮线光缆
  两类（19 行），无其他长度材料受影响。

## 5. 表四材料页重做（按宇翔表四甲截图格式）

**Bug 先查——结论：** 生成主材其实算得出（引擎 `table4A/4B` 有行、导出
表四正常），但 `WorkloadMaterialsView` 把 SwiftUI `Table` 塞进 `ScrollView`
的 VStack，Table 在滚动容器内高度塌陷，用户看不到行。且该页与全 App 的
ProTable 体系不一致。本版整页重做为 ProTable 平铺清单，结构性消除塌陷；
原“工程级修正”雏形（materialAdjust / materialPriceOverrides）并入下面
的统一工程级材料层，不留两套。

**列序（照截图）：** 代号 / 材料名称 / 规格程式 / 单位 / 数量 / 除税价格 /
材料金额 / 类型 / 类别 / 备注。甲供（表四甲）、乙供（表四乙）仍分两组两表，
安装设备页同组件按 supply=设备 渲染；导出结构不变（仍三组一表）。

**工程级材料层（数据设计，进引擎）：**
`Project` / `ProjectRecord` 新增三个向后兼容字段（缺失 = 空）：
- `materialEdits: [MaterialRowEdit]`——对生成行的覆盖，按生成行身份键
  `key = 名称|规格`（原键，改名不改键）定位：
  `code/name/spec/unit/supply/category/remark: String?` + `deleted: Bool`。
- `manualMaterials: [ManualMaterialRow]`——手工行全记录（id、code、name、
  spec、unit、qty、priceExcl、supply、category、remark）。
- `materialOrder: [String]`——行序（生成行原 key / 手工行 id 的全局序）。

`Calc.buildMatTable` 改为先生效行集再分组：
生成行（auto 数量 + 既有 delta 调整 + 既有单价覆盖）→ 套 `materialEdits`
（改名/规格/单位/类别/备注/代号、改 supply 归属、deleted 剔除）→ 并入
手工行（按自身 supply 入组、金额公式与生成行同：priceVat = 价 × 组税率）
→ 表内按 `materialOrder` 稳定排序（未列入者按生成序接末尾）→
totals 由生效行求和。于是取费（表二主材费）、表一、导出一律消费生效表四。
`Table4Row` 新增 `code/category/remark/supply/isManual`（默认值，源码兼容）；
导出表四的备注改为 `row.remark` 非空优先、否则按 `row.key` 查库备注
（与现行按 name|spec 查等价，改名后仍取原行备注）。

**可编辑性：** 除材料金额（= 数量 × 除税价，自动算）外全字段可改：
数量改 → 生成行写回 delta = 新量 − auto 量（沿用既有 materialAdjust 存储），
手工行直接改 qty；单价改 → 既有 materialPriceOverrides / 手工行 priceExcl；
类型列 = supply（select：甲供/乙供/设备，写 edit.supply 或手工行 supply）；
行可插入（onAdd 追加手工行）/删除（生成行写 deleted、手工行删记录）；
上移/下移写 materialOrder（见 §9）。不回写资料库。

## 11. v2.6.1 补记：真机三问题（2026-10-24 用户截图，默认方案自建工程）

### 11.1 问题 1a：基准行主材关联不上（TXL4-011 等，数据层脱节）

- 定位：种子 lineage（Electron 种子导入的用户库）中，TXL4-011 的光缆主材只挂在
  kind=变体 规则上（variant「敷设管道光缆 6芯」/「敷设管道光缆 12芯」），而定额
  基准名经 v2.2.0 官方正名后是「敷设管道光缆 12 芯以下」——面板/引擎的变体匹配
  是精确相等，基准行 variant=定额名命中不了任何规则 → 关联区无主材组（仪器组
  是 quotaInstruments 直挂，不受影响）。full-library lineage（通用规则）无此问题，
  故用户库（种子 lineage）独中招。
- 受害面（种子全量排查，口径：基准行命中不了任何主材规则）：27 个定额。其中
  真脱节 = 基准名含「N 芯」芯数标记的光缆/接续/交接箱类；无芯数基准名者
  （TXL5-044 槽道光缆、TXL4-053 墙壁光缆、TXL7-023/024 分纤箱、TXL7-028/029
  分路器等）本来就必须双击选型号，基准行无主材是预期行为，不修。
- 修法（数据层加载迁移，与 v2.6.0 电缆单位迁移同模式，能修用户已落盘数据）：
  `repairBaselineVariantRules(in: LibrarySet) -> Int`：对每个定额，若基准行已有
  命中规则（通用 / 变体|备选 variant==定额名 / 变体* 前缀命中）则跳过；否则从
  定额名提取芯数上限 N（正则 `(\d+)\s*芯`），取同定额 kind=变体、芯数标记
  （spec 优先、variant 兜底）≤ N 的最大者，复制一条 variant=定额名的规则
  （新 id，其余字段不变，原规则保留，短单路径不受影响）。TXL4-011 → 复制
  GYTA_12芯规则；TXL2-021「36 芯以下」→ 复制 24芯（≤N 最大）；TXL6-008
  接头盒、TXL7-042/043 交接箱同理。天然幂等（复制后基准行已命中），DbFile
  层另加 `baseline-variant-v261` 标记（用户在关联区删掉补齐规则后不再复活）。
  挂点：`DatabaseStore.repair`（既有库）+ `importProfileData`（导入的旧方案文件，
  每次导入跑一次，天然幂等）。残留：kind=备选且 variant="" 的规则（如 72芯备选）
  在现行行 variant 语义（恒为定额名/短单名）下永远命中不了——属备选语义的
  另案，不在本轮改动（改动它会改变备选含义，需用户另行裁决）。
- 验收口径：种子真实数据 + 电缆迁移在前，TXL4-011 基准行（10 千米条）关联区
  含光缆 GYTA_12芯 10150 m（10×1015，单位 m）；6芯行含 GYTA_6芯 10150 m。

### 11.2 问题 1b：变体行工日快照为 0（添加路径缺陷）

- 定位：`quotaSuggestions` 把常用短单条目合成 QuotaRow 时硬编码
  `tech: 0, labor: 0`；添加栏与定额搜索 sheet 都用此合成行快照。短单排在全库
  之前，用户最容易点到的就是短单变体行（如 TXL4-011「敷设管道光缆 6芯」），
  行快照 0/0，且 v2.6.0 的快照回填只补 nil、不覆 0 → 永久为 0。全库基准行
  （真实 QuotaRow）不受影响，故行 2 正常、行 1 为 0。
- 修法：`quotaSuggestions` 合成短单行时按 code 回查定额库补 tech/labor（库中无
  此 code 则保持 0，孤儿行由状态列提示）；unit/coef 保留短单值（短单系数是
  用户可维护的常用系数）。另补迁移 `repairBugZeroSnapshots`（标记
  `zero-snapshot-v261`）：已落盘行同时满足 tech==0 && labor==0 且库中
  tech/labor 任一非 0 → 两快照置 nil（回落库值），修复用户现有行 1；用户
  在本轮之后主动改出的 0/0 不受影响（标记只跑一次）。

### 11.3 问题 2：表三甲单击“点不动、很卡、多次点击才选上”（两主因）

- 主因 1（可测量的主因）：`AppState.calcResult(for:)` 无缓存，WorkloadView
  一次 body 求值中 `result` 经 statsStrip、orphanIds/invalidIds、警告条、
  汇总条、quantityDicts 间接访问，被重复求值十余次全量 calcFor（库约
  3000 定额 + 6600 规则）；选中行变化只改 @State，却触发整页十余次全量
  计算堵主线程 → 点击高亮迟迟不出现，用户感觉“点了没反应”。状态栏、
  侧栏工程卡片同理每 render 重算。
- 主因 2（焦点抢占）：ProCellField 失焦即提交，且 commitEdit 提交后无条件
  把编辑推进到下一行同列；编辑中单击其他行时，首击被失焦提交流程吃掉，
  且编辑态跳到下一行而非选中点击行 → “多次点击才选上”。
- 修法：① AppState 计算缓存，键 (dbGeneration, saveVersion, projectId,
  updatedAt)——db 的 @Published didSet 递增 generation；patch 必 bump
  saveVersion 且 project.updatedAt，故缓存失效口径与写路径一致；纯视图
  @State 变化（选行）零重算。② ProCellField 提交分流：回车提交才推进
  下一行，失焦提交只提交并退出编辑态（commitEdit 加 advance 参数）。
- 单元格双击手势经排查：保留（双击编辑的唯一入口）；上述两修复后首击
  丢失的两个可证实路径已消除；若真机仍有首击丢失，再做行级双击重构
  （本轮不扩大改动面）。

### 11.4 问题 3：底部汇总条被裁切/重叠 + 数字三处重复

- 3① 布局：工作量页 3a 的 VStack（页眉+统计+添加栏+分页+VSplitView+
  汇总条）最小高度在用户窗口高度下溢出——VSplitView 两子项 minHeight
  180+200 与固定 chrome 叠加，超高部分被底边裁切，汇总条（最后一项）
  半截露在状态栏下方。修法：VSplitView 子项 minHeight 降为 130/150，
  汇总条加 layoutPriority(1)（空间不足时先保汇总条，挤压由内含滚动的
  Split 吸收），汇总条不再被推出可视区。
