# v2.1.0 设计：定额库数据补全（吸纳小程序种子数据）

> 版本：v2.1.0 ｜ 日期：2026-10-22 ｜ 仓库：dujianhua200/tx-budget-mac
> 性质：**数据 + 合并工具**。计算引擎、计算口径、数据格式、xlsx 导出一字不动。

## 1. 背景与问题

用户指出：表三插入定额时，应同时带入该定额的材料、机械、仪器仪表关联，否则表三乙（机械）、
表三丙（仪表）、表四（材料）无法自动生成。这个判断成立——查实现状（App 现行种子，
即 Electron `data/seed.json`，也就是用户现用数据的来源）：

| 表 | App 现行 | 覆盖定额 | 问题 |
|---|---|---|---|
| 定额 quotas | 2,622 条 | — | 缺 547 条，其中整册 T5G（527 条）全缺 |
| 材料关联 rules | 117 条 | 54 个定额 | **最大缺口**：绝大多数定额插入后表四不出材料 |
| 机械关联 quotaMachines | 1,533 条 | 763 个定额 | 约半数定额表三乙为空 |
| 仪表关联 quotaInstruments | 1,685 条 | 575 个定额 | 同上（另有少量指向已删定额的孤儿行） |
| 台班价 machinePrices / instrumentPrices | 59 / 98 条 | — | 与小程序价目同源不同版，以 App 现价为准 |

App 的模型与引擎本来就完整支持三张关联表（证据见 §2），缺的只是数据。
用户提供了其微信小程序的种子数据导出包（`comm-budget-export-20261022.zip`，2026-10-22），
其中 `cloudfunctions/seed/quota-data.js` 含 QUOTA 3,092 条，每条内嵌
defaultMaterials（共 6,121 条，覆盖 1,514 个定额）、defaultMachines（2,156 条，覆盖 1,180）、
defaultInstruments（1,876 条，覆盖 651），另有 MACHINES 58 / INSTRUMENTS 97 条价目。
本版把这批数据转换、内置、并提供一键合并补全。

**不吸纳**：小程序全部 JS 代码、其简化费率模型（constants.js）、其 MATERIALS 占位表（仅 7 行示例/表头）。

## 2. 引擎消费路径（先证实，再补数据）

- 表三甲（工日）：`Engine/Calc.swift` §2，由 quotas 的 tech/labor × 工程量生成。
- 表三乙/表三丙：`Calc.swift` §3 `calcEquip`——按 `quotaMachines` / `quotaInstruments`
  的 (quota → mcode, qty) 展开，台班数 = 工程量 × qty，金额 = 台班数 × 台班价
  （价按 mcode 查 `machinePrices` / `instrumentPrices`；查不到价按 0 计，行仍生成）。
- 表四（材料）：`Calc.swift` §4——遍历 `rules`，按 kind 决定取量口径（见 §4），
  材料量 = 取量 × consumption；再按 (name, spec) 查 `materials` 库定供应方与单价
  （库中无此材料时用 rule.supply 兜底，单价 0 并标 unmatched）。
- 方案 → 引擎的转换在 `Logic/ProfileLibs.swift` `profileToLibs`，八张表全量透传。

结论：三张关联表补齐后，插入定额即自动生成表三乙/丙与表四，无需改任何算法。

## 4. 字段映射

### 4.1 quotas（QUOTA → QuotaRow）
`code=code`、`name=name`、`unit=unit`、`tech=skilled`、`labor=unskilled`、
`book=volume`（册全称，如“通信线路工程”；App 旧数据的 book 为短称如“电源设备册”，
仅展示字段，不参与计算，新增行用全称）、`alias=vol`（如 TXL）、`coef=1`（与 App 种子一致）。

### 4.2 quotaMachines / quotaInstruments（defaultMachines / defaultInstruments）
`quota=所在定额 code`、`mcode=model`、`mname=name`、`unit=unit`、`qty=qtyPerUnit`。
条目自带的 price 不入关联表（台班价只走价目表，见 §4.4）。

**无 model 条目的处理**（机械 651 条、仪表 225 条源数据缺编码）：
1. 先按名称解析：名称经 NFKC 归一化并去掉全部空白后，与小程序 MACHINES/INSTRUMENTS
   及 App 现行价目表的名称逐字比对，唯一命中则采用该编码
   （实测：机械 225 条、仪表 53 条可解析，含 6 条仅 App 价目表有其名如“载重汽车(12t)”→TXJ018）；
2. 仍无编码的（机械 426 条、仪表 172 条）：**保留行、mcode 置空**，不臆造编码。
   引擎对空编码按价 0 生成行——台班数正确、金额待用户在价目表补价后即准；
   合并去重时这类行以 (quota, mname) 为身份（见 §5），不会被彼此折叠。

### 4.3 rules（defaultMaterials → RuleRow）
`quota=所在定额 code`、`material=name`、`spec=spec`、`unit=unit`、
`consumption=qtyPerUnit`、`supply=supply`（缺失的 68 条按甲供，见下）。

**kind 与 appliesTo 的取值依据**（引擎语义，`Calc.swift` §4）：
- `kind == "通用"`：取量 = 该定额全部工程量（byQuota.raw，忽略 variant）；
- `kind == "变体"` / `"变体*"`：只对 variant 等于/前缀匹配的工程量行取量；
- `kind == "备选"`：仅当用户在工程中手动启用该 rule 时才生效。

小程序 defaultMaterials 是“该定额的标准材料消耗”，对该定额的全部工程量生效，
因此 **kind = "通用"、variant = ""**。`appliesTo` 引擎不读（仅库表展示/导入导出列，
语义为“适用工程”，“全”= 全部工程启用，与母版“默认行适用工程=全”一致），取 **"全"**。

源数据内同一 (quota, material, spec) 重复 5 行、其中 3 行消耗量冲突
（TXL4-055 中间支撑物 8.08/10.1、TXL3-221 与 TXL3-222 三眼双槽夹板 11.11/2.02）：
按源顺序**保留首行**，冲突在转换报告中列明。

supply 缺失（68 条）：源数据未标供应方。表四分表（甲/乙/设备）依赖 supply，
且同一材料在源数据中 supply 从不冲突（591 个材料中 0 个多值），故缺失按 **甲供**
（与 §4.5 materials 的缺失处理一致；材料行若已在用户材料库中，表四以材料库的
supply 为准，rule.supply 只是兜底）。

### 4.4 台班价（MACHINES / INSTRUMENTS → machinePrices / instrumentPrices）
`code=code`、`name=name`、`price=price`、`unit="台班"`（源价目无 unit 字段，
App 现行价目 59+98 条 unit 均为“台班”）。转换产物保留小程序全部价目（58/97 条）；
合并时**只补 App 缺失的编码、绝不覆盖现价**（见 §5）。实测对 App 现行种子：
机械新增 TXJ001 / TXJ061 / TXJ062，仪表新增 TXY001 / TXY100 / TXY101。

### 4.5 materials（由 defaultMaterials 按 (name, spec) 去重生成）
共 591 条。`unit` 取首次出现值；`priceExcl = 0`（小程序材料价不可靠：6,121 条中
仅 1 条非 0，且其 MATERIALS 单价表为占位示例——价格留给用户在材料库维护，
与 App 旧种子中用户已维护的价格互不干扰，合并只增不改）；
`supply` 取该材料出现时的 supply（源数据中从不冲突）；全部缺失的 17 个材料按甲供。

### 4.6 shortlist
小程序无对应数据，转换产物为空数组；合并永不触碰 base 的 shortlist。

### 4.7 转换产物实际计数（脚本输出，即完整库内容）

| 表 | 条数 | 备注 |
|---|---|---|
| quotas | 3,092 | 源 QUOTA 全量 |
| rules | 6,116 | 源 6,121 去重后（同键 5 行折叠） |
| materials | 591 | (name, spec) 去重 |
| quotaMachines | 2,156 | 含空编码 426（零丢失） |
| quotaInstruments | 1,876 | 含空编码 172（零丢失） |
| machinePrices | 58 | 小程序价目全量（合并时只补缺） |
| instrumentPrices | 97 | 同上 |
| shortlist | 0 | — |

行 id 由脚本确定性生成（前缀 `fl_` + 表名 + 编号/编码），与 App 既有 id 前缀
（quota_/rule_/qm_/qi_/mat_/mach_/inst_）不冲突，重复合并不会产生重复行（见 §5 幂等）。

## 5. 合并逻辑（`Logic/LibraryCompletion.swift`，纯函数、可单测）

```
补全合并(base: LibrarySet, full: LibrarySet) -> (merged: LibrarySet, report: 补全报告)
```

**总原则：只增不改。** base 中任何一行、任何字段（工日、价格、消耗量……）都不修改；
合并只把 full 中 base 没有的行追加到表尾（保持 full 内顺序），base 原行顺序不变。

| 表 | 判定键（键已存在则跳过） | 额外规则 |
|---|---|---|
| quotas | code | — |
| rules | (quota, material, spec) | quota 不在合并后定额集合中 → 孤儿跳过并计数 |
| materials | (name, spec) | — |
| quotaMachines / quotaInstruments | (quota, mcode)；mcode 为空时以 (quota, "name:"+mname) 为键 | 同上孤儿跳过 |
| machinePrices / instrumentPrices | code | 新增行价格取 full（小程序价）——仅限 base 缺失编码 |

报告含各表新增条数与孤儿跳过数。合并**幂等**：对已合并结果再合并，新增必为 0。
（共同编码的工日小程序与 App 有 119 处不一致、台班价亦不同源——全部以 App 现值为准，
靠“只增不改”天然保证，不做任何字段级调和。）

以 App 现行种子为 base 的实测新增：定额 +547、材料关联 +6,116、材料 +590、
机械关联 +667、仪表关联 +496、台班价 +3 / +3，合计 +8,422，孤儿跳过 0。
用户实际数据与种子有出入时以运行时报告为准。

## 6. UI 入口与用户流程

- 位置：**资料库页**（`LibrariesView`）页首当前方案横幅下加「补全定额库」按钮
  （资料库页的职责就是维护当前方案的库；配置方案页只管方案本身的新建/复制/删除，
  不放数据操作——与 v2 设计文档的页面职责划分一致）。
- 作用对象：当前资料库方案（`resolveEditingProfile`，与页面正在编辑的方案一致）。
- 流程：点按钮 → 先用纯函数对当前方案试算 → 弹确认框：说明“只新增、不覆盖现有
  任何数据”并列出预计新增数（定额/材料关联/机械/仪表/材料/台班价）→ 确认后经
  `AppState.updateDb` 写回并自动保存 → 弹完成报告（实际新增数与试算一致）。
- 内置完整库加载失败（资源缺失）时按钮禁用并给出提示，不静默失败。

## 8. 测试计划（总数只增不减，基线 160）

1. 合并逻辑单测：八表逐表构造“现行行 + 同键冲突行（值不同）+ 新行”，
   断言现行行逐字段不变、新行被追加、报告计数正确；空编码行以名称为键不折叠；
   孤儿关联跳过并计数；价格只补缺失编码；幂等（二次合并新增 0）。
2. 内置资源完整性：经与 App 相同的加载路径（Bundle.module）加载完整库，
   断言八表计数与 §4.7 一致（3,092 / 6,116 / 591 / 2,156 / 1,876 / 58 / 97 / 0）。
3. 引擎端到端：以 App 种子（Fixtures/seed.json）为 base 合并完整库，
   用 TXL4-026（App 中原有机械/仪表关联、**无材料关联**）建工程、工程量 2：
   断言合并前表四无其材料行；合并后表三乙 TXJ026/TXJ016 台班数 = 0.4×2、
   表三丙 TXY094/TXY095 = 0.4×2、表四甲 电缆 = 1015×2、电缆托板 = 35.35×2、
   热缩端帽(带气门) = 5.05×2（数量 = 消耗量 × 工程量）。
